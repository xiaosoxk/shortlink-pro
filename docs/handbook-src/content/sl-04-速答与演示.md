# 第4章 高频速答清单与现场演示话术

## 4.1 项目深挖速答（30 秒版）

| 问题 | 30 秒答案 |
|---|---|
| 热路径为什么快？ | 跳转只做缓存查询加队列入队，命中零 SQL；写路径全异步批写。压测 220 req/s、限流精确熔断。 |
| 短码怎么生成？ | 雪花 ID（41 位毫秒时间戳+机器号+序列，时钟回拨沿用上次时间戳耗序列）转 Base62，全局唯一零查库、趋势递增对索引友好。 |
| 为什么 302 不用 301？ | 301 被浏览器永久缓存，改址和统计都会失效；302 每次回源，配合 no-store。 |
| 缓存三问怎么防？ | 穿透：不存在 key 写负缓存哨兵；击穿：TTL+主动失效，生产补逻辑过期；雪崩：TTL 加抖动+多级缓存（README 路线图）。 |
| 缓存一致性？ | Cache-aside：读 miss 回源；写后删缓存（删除短链立即失效）；删除失败可上 MQ 重试或订阅 binlog。 |
| 分布式锁三要素？ | SET NX EX 原子加锁、唯一 token 标识持有者、Lua 比较后删除原子释放；TTL 兜底防死锁。 |
| 限流为什么选令牌桶？ | 允许突发、长期速率受控；固定窗口有临界突刺。Redis 版用 Lua 原子化，多实例共享一桶。 |
| 点击统计会不会丢？ | 队列满丢弃并计数（可丢性是设计决策），批写前进程崩溃会丢最后一批；强可靠需求改 WAL/消息队列——取舍明确说出来。 |
| 统计的实时性？ | 返回值=落库计数+缓冲区未落库计数，秒级实时；分桶曲线以落库数据为准，延迟一个 flush 间隔。 |
| JWT 放哪、怎么失效？ | Bearer 头传输；无状态令牌靠短有效期+refresh token，主动吊销用黑名单（本项目 demo 短效即可）。 |
| 密码怎么存？ | PBKDF2-HMAC-SHA256 加每用户随机盐，迭代次数入存储格式可升级；比较用 compare_digest 防时序攻击。 |
| 越权怎么防？ | 所有者校验集中在一个 get_owned；他人资源一律 404 不泄露存在性；WS 订阅同样校验归属。 |
| 中间件顺序？ | RequestContext 最外层（含限流器的日志）、RateLimit 在内；add_middleware 后加的在外层。 |
| 多 worker 部署注意什么？ | 内存限流/锁不跨进程→必须启用 Redis 后端；SQLite 换 Postgres；gunicorn 多 worker 加 Nginx。 |
| 优雅停机做了什么？ | lifespan 收尾：停消费者→flush 残余点击→关缓存/限流连接→dispose 连接池。 |
| 怎么测的？ | 38 个用例零外部依赖：ASGITransport 进程内跑完整中间件栈，每用例独立 tmp 数据库，FakeL 不需要——直接真栈测试。 |
| 压测怎么做的？ | httpx AsyncClient + Semaphore 限流并发，看吞吐与状态码分布；429 数量与阈值对账验证限流器精度。 |
| 生产化还差什么？ | Postgres+Alembic、Redis 强制、Nginx+多 worker、prometheus-client 直方图、OpenTelemetry、金丝雀发布——按 README 路线图讲。 |
| 最有成就感的点？ | 限流器 429 数量与理论阈值对账成功的那一刻——特性被定量验证，而不是"看起来能用"。 |

## 4.2 现场演示脚本

准备：`python -m uvicorn app.main:app --port 8000` 起服务；浏览器开 /docs 与控制台页。

第一步（60 秒）讲热路径：控制台创建短链→点击跳转→看 click_count 增加；打开 /metrics 指出 cache_hits_total 与 clicks_recorded_total 的变化——"每一次跳转的代价是两次内存操作"。

第二步（60 秒）讲实时：点控制台"监听"按钮（WebSocket 订阅），再点一次短链，看计数即时跳动——"房间制推送，只有主人能订阅自己的短链"。

第三步（90 秒）讲限流：跑 `python scripts/demo.py`，展示状态码分布 302/429 混合——"546 次 429 与 600/分钟阈值对账，限流器被定量验证"；随后指 /metrics 里 rate_limited_total。

第四步（60 秒）讲测试与代码：`python -m pytest -q` 秒级 38 passed；打开 middleware.py 讲纯 ASGI 与 ContextVar，打开 link_service.py 讲负缓存。

## 4.3 STAR 结构的项目陈述（2 分钟版）

S：需要一个大项目证明后端工程能力，要求考点密度高且可运行可验证。
T：实现一个短链接服务，覆盖认证、发号、热路径缓存、限流、异步统计、实时推送与可观测性，并全部量化验证。
A：设计"热路径零 SQL"架构；自研 JWT/雪花 ID/令牌桶/分布式锁四个安全与并发原语（都有单后端与 Redis 双实现）；点击埋点做成生产者-消费者批写；38 个测试锁行为；压测定量对账。
R：38 用例全绿；压测 220 req/s 且 429 与阈值精确吻合；已开源，并沉淀了六个带排查链路的真实踩坑（第 3 章）。
