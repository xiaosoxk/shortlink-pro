# 第3章 踩坑实录：真实调试记录

本章六个坑全部来自 ShortLink Pro 的真实开发过程，每个按"现象→排查→根因→修复"展开。它们比任何八股都能证明代码归属，因为排查链路只有亲手调过的人才讲得出来。

## 3.1 坑一：一行漏掉的类型注解，全站接口 422

现象：注册/登录等几乎所有接口返回 422 Unprocessable Content，报错定位在 `['query', 'request']`，"Field required"——一个叫 request 的查询参数居然是必填的？

排查：先做最小复现（一个只含 `async def x(request: Request)` 的应用，正常），排除框架版本问题；再用 `get_typed_signature` 打印 FastAPI 解析后的参数注解，发现问题不在出问题的端点上，而在它们共同依赖的 `get_session`：

```python
# 错误写法：request 没有类型注解
async def get_session(request) -> AsyncIterator[AsyncSession]:
```

根因：FastAPI 识别依赖参数**只看类型注解**。无注解的参数会被当作"必需的查询字符串参数"，于是每个用了 `Depends(get_session)` 的接口都在校验一个永远不存在的 query 参数 request。

修复：补上 `request: Request` 注解，并在 docstring 里写明这个坑。教训：框架的魔法建立在注解之上，Python 里"能跑"和"被框架正确理解"是两回事；排查依赖类 422 时先看依赖函数自己的签名，而不是端点签名。

## 3.2 坑二：WebSocket 关闭码总是 1000，而不是我发的 4401

现象：无 token 的 WebSocket 握手，服务端明确 `close(4401)`，测试却总是收到 1000（正常关闭）。

排查：在应用外面包一层"间谍"中间件，直接打印 ASGI 出站消息——看到的是 `{'type': 'websocket.close', 'code': 1000}`，说明 4401 根本没发出去。继续追：这条 close 来自路由匹配阶段，而我的 WS 路由压根没注册（main.py 忘了 include ws.router）。Starlette 对**未匹配的 WebSocket 连接**的默认行为就是发 close(1000)，不是 404。

根因：路由注册遗漏 + 对框架"未匹配 WS"默认行为不了解。

修复：补 include；测试断言改为"特定关闭码"以防止回归。教训：WebSocket 的错误语义要自己用关闭码约定（4401 未认证、4403 越权、4404 不存在），并且必须有测试锁定；排查这类问题，包一层 ASGI send 打印消息是最直接的观测手段。

## 3.3 坑三：TestClient 的 WebSocket 在握手期就抛异常

现象：修完路由后，"越权监听"测试里 `pytest.raises(WebSocketDisconnect)` 包住了 `receive_json()`，仍然失败——异常在更早的地方抛出。

根因：服务端"未 accept 就 close"发生在**握手阶段**，Starlette 的 TestClient 会在进入 `websocket_connect()` 上下文时直接抛 WebSocketDisconnect，根本到不了 receive。

修复：把 raises 包住 connect 本身：

```python
with pytest.raises(WebSocketDisconnect) as exc_info:
    with tc.websocket_connect(f"/ws/links/{code}?token={bad}"):
        pass
assert exc_info.value.code == 4403
```

教训：测试替身（TestClient）的异常抛出时机要与真实协议阶段对齐，写测试前先确认"这个错误发生在协议的哪一步"。

## 3.4 坑四：ImportError greenlet——asyncio 栈的第一道门槛

现象：首次运行，`from sqlalchemy.ext.asyncio import ...` 直接 ImportError，提示需要 greenlet。

根因：SQLAlchemy 的 asyncio 扩展依赖 greenlet 做"协程与同步上下文的双向桥接"（run_sync 就靠它把同步代码包进绿色线程执行），但 greenlet 是平台相关包，`pip install sqlalchemy` 默认不装，必须用 `sqlalchemy[asyncio]` extras。

修复与沉淀：requirements.txt 固定写 `sqlalchemy[asyncio]`；向别人讲解 SQLAlchemy async 原理时，greenlet 桥接正是"为什么 async ORM 里不能混同步驱动"的技术根源，是必讲点。

## 3.5 坑五：测试数据违反自家校验规则

现象：限流测试用用户名 "rl"（2 个字符）注册，得到 422 而不是预期的 201——限流还没触发，先被自己的参数校验拦住了。

根因：UserCreate 规定用户名 3~32 字符，测试数据手工编写时没对齐 schema。

修复与沉淀：测试数据尽量由同一套校验规则生成或校验；更重要的是借这个点向面试官展示"校验即接口契约"——422 返回体里明确指出 min_length=3，这正是 Pydantic v2 自动生成的价值。另有一个同族坑：WebSocket 测试最初共享固定 DB 文件，第二次运行时别名冲突 409 导致 KeyError——改为 pytest 的 tmp_path 每用例独立数据库，测试从此可重复。

## 3.6 坑六：压测里"混进来的 429"到底是不是 bug

现象：demo 脚本 1200 次并发跳转，结果 654 个 302、546 个 429——第一反应是"服务有 bug"。

排查与定性：跳转限流配置是 600/分钟，654 ≈ 600（令牌桶容量）+ 突发余量，429 的数量与阈值完全吻合——这不是 bug，是限流器在精确工作。

处理：把"429 混合分布"变成 demo 的展示点（状态码分布打印进压测报告），并另写独立测试：把阈值调到 3 次/分钟，精确验证第 4 次请求 429 且响应带 Retry-After。教训：**异常行为的定量对账**（数量对得上阈值）是把"疑似 bug"转成"被验证的特性"的关键一步，也是压测分析的基本功。

## 3.7 方法论沉淀

六个坑的共同线索：第一，错误信息里藏着定位钥匙（422 的 loc、关闭码 1000、测试断言的差值），先读懂再动手；第二，最小复现是分离"框架行为"与"业务代码"的唯一手段；第三，每个坑修完都要用测试锁住，否则必然复发。这三条在面试中可以作为"你怎么保证不再犯"的标准答案。
