# 第2章 核心模块逐段精讲

## 2.1 手写 JWT 与密码哈希（core/security.py）

### 为什么手写

HS256 的 JWT 线格式只有三段 base64url：header.payload.signature，签名就是 HMAC-SHA256(secret, "header.payload")。手写一遍之后，任何关于 JWT 的面试题都能对着字节讲。同时天然覆盖最经典的攻击——alg 混淆：解码时强制校验 alg 必须是 HS256。

```python
def jwt_decode(token: str, secret: str) -> dict:
    try:
        header_b64, payload_b64, signature_b64 = token.split(".")
    except ValueError as exc:
        raise TokenError("malformed token") from exc
    try:
        header = json.loads(_b64url_decode(header_b64))
        if header.get("alg") != "HS256":      # 防 alg 混淆（拒绝 none/RS256 伪造）
            raise TokenError("unexpected algorithm")
        signing_input = f"{header_b64}.{payload_b64}".encode()
        expected = hmac.new(secret.encode(), signing_input, hashlib.sha256).digest()
        if not hmac.compare_digest(expected, _b64url_decode(signature_b64)):
            raise TokenError("bad signature")   # 常数时间比较，防时序攻击
        payload = json.loads(_b64url_decode(payload_b64))
    except TokenError:
        raise
    except Exception as exc:
        raise TokenError("malformed token") from exc   # 二进制垃圾也归一为 TokenError
    ...
```

三个细节是讲解重点：第一，签名校验用 `hmac.compare_digest` 而非 `==`——比较耗时与内容无关，攻击者无法靠响应时间逐字节猜签名；第二，整个解码过程用兜底 try 包住，因为伪造 token 可能是任意二进制（实测踩到过 UnicodeDecodeError 穿透成 500，见第 3 章坑三的姊妹问题）；第三，TokenExpiredError 单独细分，前端可据此引导重新登录。

密码哈希选 PBKDF2-HMAC-SHA256（标准库 hashlib 自带）：`pbkdf2_sha256$iterations$salt_hex$hash_hex` 的存储格式让迭代次数可随算力升级。对应的测试覆盖了弱密码拒绝、错误口令 401、登录失败文案统一（防用户名枚举）。

## 2.2 雪花 ID 与 Base62（core/snowflake.py）

64 位布局：1 符号位 + 41 毫秒时间戳 + 10 位机器号 + 12 位序列号，单机每毫秒 4096 个，自定义纪元可用 69 年。短码 = base62(雪花 ID)，全局唯一所以生成时零查库，且趋势递增对 InnoDB 聚簇索引友好（避免 UUID 随机写导致的页分裂）。

时钟回拨处理是必讲点：检测到当前时间小于上次发号时间（NTP 校时回拨），不抛异常也不等待，而是**沿用上次的时间戳继续消耗序列号**；序列号耗尽才自旋等待追平。加 threading.Lock 保证多线程安全——测试里 4 线程各取 2000 个，8000 个 ID 无一重复且单调递增。

> 追问：为什么不用数据库自增？答：自增在分库分表时要额外协调，且暴露业务量（短码可被遍历）；雪花ID + base62 同时解决唯一性、趋势性、不可猜测性。更短码位（如 7 位）方案：号段预取或哈希+冲突重试，代价是要查库，本项目在 README 权衡过。

## 2.3 令牌桶限流与分布式锁（双后端策略模式）

三个"有 Redis 用 Redis、没 Redis 用内存"的后端（cache/limiter/lock）共用同一套设计：抽象基类定义接口，工厂函数启动时 ping Redis，失败打警告并降级内存实现。业务代码只依赖抽象，这就是项目能"零依赖演示、配 Redis 上生产"的原因。

内存令牌桶的核心：`tokens = min(capacity, tokens + elapsed * rate)`，够 1 个就扣减放行。Redis 版把"读桶-补币-扣币-写回"压进一段 Lua 脚本，利用 Redis 单线程执行保证原子——多实例共享同一个桶也不丢精度。限流中间件按路径分桶（API 120/分钟、跳转 600/分钟），命中直接返回 429 加 Retry-After，并区分 X-Forwarded-For 仅在可信代理后启用（注释里写明信任边界）。

分布式锁的三个教科书细节全部落地：加锁 `SET key token NX EX 30`（原子）；value 用随机 token 标识持有者；释放用 Lua 做"比较 token 再删除"——GET 与 DEL 分两步的话，锁过期后被别人抢走就会误删他人的锁。

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else return 0 end
```

## 2.4 cache-aside 与负缓存（link_service.resolve）

读路径：查缓存→miss 查库→回填。两个增强：不存在的短码写入负缓存哨兵（TTL 30 秒），第二次查询直接在缓存层拒绝，**防缓存穿透**（恶意刷不存在 key 打穿到库）；删除短链后主动 `cache.delete` 失效，保证"删除后跳转立即 404"的最终一致性。命中缓存后仍校验 is_active 与 expires_at——缓存的是数据不是放行决定，过期短链不能因为缓存还在就继续跳（对应测试 test_expired_410）。

> 追问：缓存击穿怎么办？答：本项目热点 key 用较长 TTL + 删除时主动失效；真正的击穿防护（互斥重建/逻辑过期）在 README 生产化路线里说明——单机内存缓存场景下"逻辑过期+异步刷新"性价比最高。

## 2.5 点击埋点：生产者-消费者批写与优雅停机（services/analytics.py）

设计动机：热点短链跳转 QPS 远超数据库写入能力，热路径绝不能同步 INSERT。方案：跳转只做 `queue.put_nowait`（队列满则丢弃并计数 clicks_dropped_total——**统计允许少量丢失，绝不反压跳转**，这条取舍要主动讲）。两个后台任务消费：_consume 从队列搬进内存缓冲，_flush_loop 按间隔或攒批把缓冲一次性 executemany 落库，并按 link_id 聚合更新反范式计数 click_count（列表页免聚合查询）。

优雅停机顺序（main.py lifespan 的 finally 段）：停消费者任务 → flush 残留缓冲（不丢最后一批数据）→ 关缓存/限流连接 → dispose 引擎池。统计接口返回"落库计数 + 缓冲区未落库计数"，兼顾持久性与秒级实时。

> 追问：为什么不用 Celery？答：埋点是"高频、可丢、无复杂编排"的场景，进程内队列 + 批写是开销最低的解；Celery 的价值在跨进程可靠投递与定时任务编排，此处用它是杀鸡用牛刀且多一个故障面。

## 2.6 纯 ASGI 中间件、链路日志与指标

中间件手写纯 ASGI 形式（`__call__(scope, receive, send)` 包一层 send_wrapper），不用 BaseHTTPMiddleware——后者有额外任务包装与流式响应坑，而且纯 ASGI 版能顺带讲清协议本身。RequestContext 中间件生成 12 位 hex request_id 存入 **ContextVar**（异步安全的"协程级全局变量"），同请求内所有日志自动带 rid，并写入响应头 x-request-id 与 x-process-time-ms。

指标（metrics.py）刻意不引 prometheus-client：Counter 加 render() 输出 Prometheus 文本格式，证明"指标只是带约定的计数器"；gauges 暴露队列深度、WebSocket 连接数、缓存条目。压测时用 429 计数直接验证限流生效。

## 2.7 WebSocket 房间制（ws.py）

ConnectionManager 用 dict[code, set[WebSocket]] 维护房间；跳转触发 broadcast_click 推给该短码的所有订阅者，发送失败的连接即时清理（单个客户端掉线不影响其他人）。鉴权两个细节：token 经查询串传入（浏览器 WebSocket 无法自定义请求头，本身是个小考点）；只有链接主人能订阅自己的短链（越权监听以 4403 关闭，无 token 以 4401 关闭，测试均有覆盖）。
